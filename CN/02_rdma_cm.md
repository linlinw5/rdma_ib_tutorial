# 第二章：RDMA 连接管理

上一章提到：RDMA RC 在传输之前需要建立连接。以 Write 操作为例，发送方的网卡需要知道对端的 QPN、目标内存地址、rkey 等关键信息，才能构造出合法的报文发出去。这些信息在通信开始之前必须由双方提前协商好。这个建立连接的阶段被称为 bootstrap。

对于 bootstrap 阶段，业界普遍有两种解法：

**带外通信（Out-of-band）**：用另一套传输通道（例如以太网 + TCP/IP）先把这些信息交换好，再开始 RDMA 通信。最常见的做法是用 TCP Socket：两端先建一条 TCP 连接，把各自的 QPN、内存地址、rkey 等信息互相发过去，握手完成后再切换到 RDMA 传输。

**带内通信（In-band）**：直接用 RDMA 网络自身提供连接建立和地址交换的服务，不依赖额外的传输通道。这套机制叫做 RDMA CM（Connection Manager）。

---

## 2.1 需要交换哪些信息

以 RC 为例，双方至少需要交换以下信息，才能让 QP 进入可以收发数据的状态：

- **QPN（Queue Pair Number）**：对端 QP 的编号，相当于 RDMA 世界里的"端口号"，告诉网卡数据要交给对方哪个 QP。

- **PSN（Packet Sequence Number）**：初始报文序列号，用于接收端校验报文顺序。

- **虚拟内存地址与 rkey**：这两项只有单边操作（例如：Write、Read）才需要。发送方要直接操作对端内存，必须知道目标内存的虚拟地址以及对应的 rkey（远端访问密钥）。双边操作（Send）由接收方自己决定数据落到哪块缓冲区，发送方不需要知道对端的内存地址，因此也不交换这两项。

- **GID/LID（IB 的寻址信息）**：有个反直觉的东西，既然双方在交换通信信息，那么肯定是已经知道对端的地址了，为什么这里还要交换 IB 寻址信息呢？这其实是个工程实践的问题。应用软件（例如：AI训练框架）往往活在 IP 的世界里，但是 GPU/CPU 需要通过 IB 访问远端机器的内存，这就需要知道对端在 IB 中的寻址信息。

---

## 2.2 带外方式：用 TCP 交换信息

带外方式的思路简单直接：在 RDMA 通信之前，先通过 TCP 建立一条普通连接，交换前面提到的连接信息。双方拿到这些信息后，各自完成 QP 的状态配置，然后开始 RDMA 数据传输。

纵观当前业界主流的 RDMA 测试软件和应用，采用 TCP 建立 QP 后，在工程落地上还存在一些实现差异，具体取决于应用开发者或架构师的选择：

- **是否需要保留 TCP 连接不挂断，协议层面没有强制要求。** 信息交换完成后，QP 已经维护了连接状态，因此从原理上讲，这条 TCP 连接可以立即断开。但很多实现会选择继续保留它，将其作为心跳通道或异常检测手段。一旦 TCP 连接断开，就可以判断对端可能出现故障，从而触发重连或错误处理。保留还是断开，本质上是可靠性和资源消耗之间的权衡，没有唯一正确的答案。

- **底层网络类型会影响带外方式的部署架构** 在 InfiniBand 网络中，IB Fabric 本身通常不负责承载 TCP/IP 流量，因此带外通信必须依赖一套独立的以太网。而在 RoCEv2 网络中，RDMA 本身运行在以太网上，带外的 TCP 连接可以直接复用现有链路，无需额外硬件。因此，IB 方案通常需要为“控制面”单独建设一张网络，而 RoCEv2 方案则可以让控制面和数据面共用同一张以太网。

---

## 2.3 带内方式：RDMA CM

带外方式的问题在于，它把连接管理的责任全扔给了应用程序：你得自己写 TCP 握手逻辑，自己定义地址交换的格式，自己决定连接的生命周期。对于需要管理大量连接的系统，这套代码并不轻松。

RDMA CM（Connection Manager）是 Linux 内核提供的连接管理机制，它将上述握手过程进行了封装，通过 RDMA 网络自身完成地址解析和连接协商，不再需要应用程序额外维护一条 TCP 通道。

RDMA CM 最实用的地方在于，提供了一套与 Socket API 高度对应的编程接口。换句话说，**RDMA CM 可以看作是用来平替带外 TCP 那套握手代码的**，熟悉 TCP 编程的开发者几乎可以直接套用 Socket 的编程思路。两套 API 的对应关系大致如下：

| Socket API  | RDMA CM API         | 作用             |
| ----------- | ------------------- | ---------------- |
| `socket()`  | `rdma_create_id()`  | 创建一个通信端点 |
| `bind()`    | `rdma_bind_addr()`  | 绑定本地地址     |
| `listen()`  | `rdma_listen()`     | 监听连接请求     |
| `connect()` | `rdma_connect()`    | 发起连接         |
| `accept()`  | `rdma_accept()`     | 接受连接         |
| `close()`   | `rdma_destroy_id()` | 销毁端点         |

在 rdma_connect() 和 rdma_accept() 的过程中，RDMA CM 会自动完成 QPN、PSN 等连接信息的交换，以及 QP 的状态迁移，开发者无需手动处理这些底层细节。连接建立之后，数据传输阶段仍然使用标准的 Verbs 接口，RDMA CM 只负责连接建立过程，并不介入数据路径。

更重要的是，RDMA CM 建立连接采用的是带内方式。对于纯 InfiniBand 网络而言，这意味着连接建立过程无需额外部署以太网，只依赖 IB 网络自身即可完成。

---

## 2.4 IB 寻址信息

前面我们提到，通信双方在建立连接时需要交换一些寻址信息。由于底层网络类型（IB/RoCEv2）以及连接建立方式（带内/带外）的不同，实际处理方式也有所区别。

RoCEv2 场景相对简单。由于 RoCEv2 运行在以太网上，GID（Global Identifier）直接由网卡的 IP 地址派生而来，两者实际上是同一个地址在不同协议层的两种表现形式。

- 在带外 TCP 方式下，双方将各自的 GID 打包进握手消息并互相交换；
- 在 RDMA CM 方式下，应用程序只需要提供对端的 IP 地址，CM 内部会自动完成 GID 解析，应用层完全不需要感知 GID 的存在。

> 备注：在 RoCEv2 中，GID 身兼两职：对于 RDMA 层来说，它是端点标识；对于 RNIC 硬件来说，它同时也是构建外层 IP 头的重要信息来源。

纯 IB 场景则相对复杂，因为 IB 拥有自己独立的寻址体系。其中，LID（Local IDentifier） 由 SM 动态分配，而 GID 与 IP 地址之间也不存在天然的映射关系。

- 在带外 TCP 方式下，双方必须通过 TCP 通道显式交换 LID 或 GID。
- 在 RDMA CM 方式下，这些工作则由 CM 内部完成。传统做法是借助 IPoIB 将 IP 地址映射为 GID，然后根据 GID 查询 SA Path Record；现代也可以直接使用原生 IB 地址（GID），跳过地址映射，直接查询 SA Path Record。完成地址和路径解析后，CM 会在 IB 网络内部完成后续握手过程，整个过程对应用程序完全透明。

> 备注：这里不必过于纠结 GID 和 IB 寻址的细节，第八章《InfiniBand 基础》会对 IB 的寻址体系和地址解析过程进行详细介绍。

## 2.5 实际使用场景

两种方式解决的是同一个问题：在 RDMA 数据传输开始之前，把 QPN、PSN、内存地址、rkey 这些参数安全地送到对端。

从实际使用来看，不同软件栈的选择差异很大：

IB 场景下，两种方式并存，分界线在于软件栈的定位。

- 生产环境的 IB 集群几乎都配有管理以太网，带外方式可以直接复用它。NCCL（NVIDIA Collective Communications Library）就是这样做的：bootstrap 阶段走带外的 TCP socket 交换 QPN 和 rkey，RDMA 数据传输阶段走 IB，全程不依赖 RDMA CM。

> NCCL 选择 TCP bootstrap 有一个根本原因：应用框架完全活在 IP 地址的世界里，不需要感知 IB 的寻址体系（LID、GID）。IB 网络被当成一条纯粹的高速通道，rank（独立的计算执行单元）的发现和连接管理全部在 IP 层完成。并且，bootstrap 代码在 IB 和 RoCEv2 上可以完全复用，多 QP、多 rail 的拓扑管理和容错逻辑也由框架自己掌控。

- HPC 领域的 MPI/UCX 则走另一条路，用 IB 自身的 UD（Unreliable Datagram）做 wireup，在 IB 网络内部完成 RC QP 的连接建立，真正做到不依赖任何带外通道。
- 存储协议栈（NVMe-oF、iSER）则更倾向于 RDMA CM，其看重的是标准化接口和运维可操作性。

RoCEv2 场景下，AI 训练框架的逻辑与 IB 场景完全一致。

- NCCL、PyTorch distributed 同样用 TCP socket 或 MPI 集合操作完成 bootstrap。
- 存储协议栈同样偏向 RDMA CM。底层换成 RoCEv2，软件栈的选择逻辑没有任何变化。

这背后有一条贯穿始终的分界线：应用框架选带外，协议栈选带内。

- 框架需要自己掌控寻址、拓扑、容错，带外方式给了它完整的控制权；
- 协议栈需要标准化接口和互操作性，RDMA CM 的 Socket 类 API 恰好满足这个需求。

无论哪种方式握手结束之后，数据路径是完全一样的：标准的 Verbs 操作，相同结构的 IB 报文。后面的章节会通过抓包，让你看到这些在 bootstrap 阶段交换的参数是怎么出现在实际报文里的。

## 2.6 NCCL 与 RDMA 的关系

在 AI 领域经常被提及的一个词就是 NCCL（NVIDIA Collective Communications Library），它和 RDMA 到底是什么关系呢？

NCCL是 NVIDIA 推出的集合通信库，专为多 GPU 分布式训练场景设计。在大模型训练中，数以百计乃至千计的 GPU 需要在每一轮迭代后同步梯度，这个过程涉及复杂的跨节点数据交换。NCCL 将这一复杂性封装起来，向上层 AI 框架（PyTorch、JAX 等）提供 AllReduce、AllGather、Broadcast 等集合通信原语，开发者只需调用一个 `ncclAllReduce()`，跨节点的梯度同步便自动完成，无需关心任何网络细节。

NCCL 与 RDMA 的关系，可以用 **C 语言与汇编语言**来类比。

- RDMA 是"汇编语言"：操作精确但偏向底层，使用者需要亲自管理 QP、MR、WR、CQ，明确告知硬件"将数据写到对端的某个内存地址"；
- NCCL 则是"C 语言"：它在 RDMA 语义之上构建了更高层的抽象，将 QP 建立、内存注册、ring 算法分片、多步传输等细节全部封装在内部，对上层框架完全透明。就像 C 程序员不需要关心 `c = a + b 被编译成了多少条汇编指令`，AI 框架工程师也无需关心 `一次 AllReduce 背后究竟发出了多少个 RDMA WRITE`。

NCCL 让 AI 应用开发者从网络复杂性中解放出来。但站在网络工程师的角度，NCCL 却更像一个"黑盒"。因为 NCCL 的每一次集合通信操作，在底层最终都会被分解为一系列 RDMA 动作，然后在 IB 或 RoCE 网络上逐一执行。所以，对于网络工程师来说，理解 AI Networking，依然要从 RDMA 入手。
